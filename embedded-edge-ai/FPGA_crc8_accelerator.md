# FPGA CRC-8 Accelerator with MicroBlaze and AXI4-Lite

A custom VHDL CRC-8 peripheral, attached to a MicroBlaze soft processor over AXI4-Lite and driven by bare-metal C, running on a Digilent Basys 3 (Xilinx Artix-7) board. The MicroBlaze application computes every CRC twice — once in software and once through the memory-mapped hardware peripheral — compares the two, and reports the outcome over UART, on the LEDs, and on the seven-segment display.

CRC-8 itself is deliberately simple. The engineering focus is the full hardware/software path: RTL datapath and control, a register-level peripheral interface, SoC integration in Vivado IP Integrator, embedded driver code in Vitis, and validation from behavioral simulation through a 12-case test suite on the physical board.

**Tools:** VHDL · C · Vivado 2024.2 · Vitis Unified IDE 2024.2 · MicroBlaze · AXI4-Lite · AXI UART Lite · AXI GPIO · Basys 3 (XC7A35T-1CPG236C)

**Demo:** [media/demo.mp4](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/media/demo.mp4) (87 s, 17.5 MB)

## Key Features

- **Bit-serial CRC-8 core in VHDL** ([rtl/crc8_core.vhd](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/rtl/crc8_core.vhd)): polynomial `0x07`, initial value `0x00`, MSB-first, one bit per clock, eight clocks per byte, with `start`/`init`/`busy`/`done` handshaking.
- **Persistent CRC state across bytes**, so messages of any length are processed by writing bytes one at a time; software issues INIT only at a message boundary.
- **Custom AXI4-Lite peripheral** ([hardware/ip_repo/crc8_axi_1_0/](https://github.com/mattdisk/FPGA_crc8_accelerator/tree/main/hardware/ip_repo/crc8_axi_1_0)) with four 32-bit registers (DATA, CONTROL, STATUS, RESULT), one-clock START/INIT pulses generated from CONTROL writes, and a sticky DONE flag for polling software, packaged as a Vivado IP.
- **MicroBlaze system** built in IP Integrator: 128 KB local BRAM, AXI SmartConnect, UART Lite at 115200 baud, one AXI GPIO for the 16 LEDs, a second 12-bit AXI GPIO for the seven-segment display, clocking wizard, reset controller, and debug module.
- **Bare-metal C driver and test harness** ([software/main.c](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/software/main.c)): software reference CRC, register-level peripheral access, bounded polling with timeout, 12 test cases, software-multiplexed seven-segment output.
- **Validation at two levels:** a self-checking VHDL testbench for the core, and hardware-vs-software comparison on the physical board.

## CRC-8 Implementation

| Parameter | Value |
|---|---|
| Width | 8 bits |
| Polynomial | `0x07` (x⁸ + x² + x + 1) |
| Initial value | `0x00` |
| Bit order | MSB first, no input/output reflection |
| Final XOR | none |
| Check value (`"123456789"`) | `0xF4` |

The core keeps an 8-bit CRC register, a shift register holding the current input byte, and a 3-bit counter. On each processing clock it computes `feedback = crc[7] XOR data[7]`, shifts both registers left, and XORs the CRC with `0x07` when feedback is `1`. After the eighth bit, `busy` drops and `done` pulses for one cycle.

Control is a small two-state FSM (idle / busy) with a fixed priority:

1. `reset` clears all state.
2. `init` (only while idle) clears the CRC register to `0x00`.
3. `start` (only while idle) latches `data_in` and enters busy.
4. While busy, one bit is processed per clock.

Because `init` does not touch the CRC register between bytes, consecutive `start` commands continue the same running CRC — this is how variable-length messages are handled. `init` and `start` are both ignored while busy, so a second command cannot restart or clear a byte in flight. `crc_out` is wired directly to the CRC register.

The design is intentionally bit-serial; there is no byte-parallel (table or unrolled XOR) datapath and no pipelining.

## AXI4-Lite Register Map

| Offset | Register | Access | Fields |
|---|---|---|---|
| `0x00` | DATA | read/write | input byte in `[7:0]`, wired to the core's `data_in` |
| `0x04` | CONTROL | write (reads return last value written) | bit 0 = START, bit 1 = INIT |
| `0x08` | STATUS | read | bit 0 = BUSY (live), bit 1 = DONE (sticky) |
| `0x0C` | RESULT | read | current CRC register in `[7:0]` |

The register map is implemented in [crc8_axi_slave_lite_v1_0_S00_AXI.vhd](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/hardware/ip_repo/crc8_axi_1_0/hdl/crc8_axi_slave_lite_v1_0_S00_AXI.vhd), with offsets and bit positions matching the constants in `main.c`. The peripheral is the Vivado-generated AXI4-Lite slave template (handshaking and register storage) with custom logic added. That logic instantiates `crc8_core` in the same clock domain and drives three things the processor relies on:

- **One-clock START/INIT pulses.** When a write to CONTROL arrives, bits 0 and 1 of the write data are registered into `start_pulse` and `init_pulse`, which then fall back to `0` on the next clock. The core therefore sees exactly one command per software write, even though the CONTROL register keeps its value.
- **Sticky DONE.** The core's `done` is a one-cycle pulse that software polling over AXI would almost certainly miss. The wrapper sets `done_sticky` on that pulse and holds it until the next START or INIT pulse (or AXI reset) clears it, so STATUS reads after completion see DONE, and each new byte starts with DONE low.
- **Live result and busy.** RESULT and the BUSY bit are driven directly from the core's `crc_out` and `busy`. They need no software-visible copy step.

## MicroBlaze Software Integration

[software/main.c](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/software/main.c) talks to the peripheral with `Xil_Out32` / `Xil_In32` at the base address generated by Vitis. For each test message it:

1. Computes the reference CRC in C (bitwise, same parameters as the hardware).
2. Writes INIT to CONTROL to clear the hardware CRC state.
3. For each byte: writes it to DATA, writes START to CONTROL, then polls STATUS until DONE is set — giving up after 1,000,000 polls and reporting `TIMEOUT` instead of hanging.
4. Reads RESULT.
5. Compares hardware against software (and against a known expected value where one is given).
6. Prints the data, both CRCs, and PASS/FAIL over UART.
7. Shows the hardware CRC as two hex digits on the seven-segment display for about two seconds, refreshing the multiplexed digits in software.

After all 12 tests it prints a pass count and drives LED0 (all passed) or LED1 (any failure).

In the original setup, the program was not stored in the bitstream. The Vitis launch configuration programmed the FPGA with the final bitstream (the same file as [hardware/bitstream/system_wrapper.bit](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/hardware/bitstream/system_wrapper.bit)), then downloaded the application ELF into MicroBlaze local memory over JTAG and started it. That run produced the recorded demonstration.

## Verification and Results

> The results below were recorded during original development and are reported from the project's original write-up and screenshots. They were **not** re-run when this repository was organized.

**RTL simulation.** The testbench [rtl/crc8_core_tb.vhd](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/rtl/crc8_core_tb.vhd) applies reset, INIT, and the byte `0x31`, then asserts that the result is `0x97`. The waveform shows `busy` covering eight clock cycles and the CRC stepping `00 → 07 → 09 → 12 → 24 → 48 → 97`.

![CRC-8 core simulation waveform](https://raw.githubusercontent.com/mattdisk/FPGA_crc8_accelerator/main/media/crc8_simulation_waveform.jpg)

**Hardware validation.** The 12-case suite ran on the physical Basys 3 board, with software and hardware CRCs matching in every case: **12 / 12 PASS**. Coverage includes the `"123456789"` check vector (`0xF4` from both paths), single bytes `0x31`, `0x00`, `0xFF`, all-zero, all-one, alternating, and repeated patterns, the multi-byte message `"ABC"`, INIT before a calculation (after deliberately leaving non-zero state), INIT between messages, and back-to-back independent operations. The full table is in [docs/design-and-validation.md](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/docs/design-and-validation.md#hardware-test-suite).

**Implementation (complete MicroBlaze system, post-implementation).** These figures cover the entire design — processor, local memory, interconnect, UART, GPIO, clocking, and the CRC peripheral together.

| Metric | Result |
|---|---|
| Worst negative slack (setup) | +1.597 ns |
| Total negative slack | 0.000 ns |
| Worst hold slack | +0.021 ns |
| Failing endpoints | 0 |
| LUTs | 1,903 / 20,800 (9.15%) |
| Flip-flops | 1,952 / 41,600 (4.69%) |
| BRAM tiles | 32 / 50 (64%) |

BRAM usage is dominated by the 128 KB MicroBlaze local memory, not the CRC datapath.

**Custom peripheral alone (standalone synthesis).** A separate synthesis run of the `crc8_axi` peripheral by itself (AXI4-Lite slave, control logic, and CRC core), made while it was being packaged, reported:

| Resource | `crc8_axi` alone, post-synthesis |
|---|---|
| LUTs | 70 |
| Flip-flops | 102 |
| BRAM | 0 |
| DSP | 0 |

The two tables have different scopes and come from different tool stages: one is the complete system after implementation, the other is one peripheral synthesized as its own top-level design. They are not directly comparable, and the system figures should not be read as the cost of the CRC accelerator. The timing and utilization screenshots and the original text reports are linked from the [design document](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/docs/design-and-validation.md#implementation-results).

## Performance Interpretation

The CRC datapath needs eight clock cycles per byte: about 80 ns at 100 MHz. That number is the core's processing time only. Each byte in the actual system also costs two AXI4-Lite writes, at least one AXI4-Lite read for polling, and the MicroBlaze instructions around them, and the final result needs another read.

No timing comparison between the hardware path and the C reference was measured, so this project makes no speedup claim. For a byte-at-a-time, register-polled peripheral, bus and software overhead is likely to dominate, and a software loop on the same processor may well be competitive. Streaming interfaces (AXI-Stream or DMA) and a byte-parallel datapath would be the natural next steps if throughput mattered.

## Source Availability and Reproduction

**Original environment:** Digilent Basys 3 (Artix-7 XC7A35T-1CPG236C), AMD Vivado 2024.2, AMD Vitis Unified IDE 2024.2, standalone (bare-metal) MicroBlaze platform, serial terminal at 115200 baud.

This repository holds the design inputs and key artifacts of a completed project. It is not a turnkey build: there is no Vivado project file and no build script, and **no rebuild has been attempted from a clean clone of this repository**.

| Item | Status |
|---|---|
| CRC core and testbench | Included; self-contained |
| Custom AXI4-Lite IP (`xilinx.com:user:crc8_axi:1.0`, revision 3) | Included in [hardware/ip_repo/crc8_axi_1_0/](https://github.com/mattdisk/FPGA_crc8_accelerator/tree/main/hardware/ip_repo/crc8_axi_1_0), with HDL and packaging metadata. Name, version, and revision match the block design. |
| Block design and IP configurations | [system.bd](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/hardware/bd/system/system.bd) together with all 14 `.xci` files it references, in the `ip/` layout it expects, plus the saved diagram layout |
| Seven-segment constraints | Included. Clock, reset, UART, and LED pins were assigned through the Basys 3 board files (board flow), so no XDC exists for them. |
| Final hardware export (XSA) | [hardware/export/crc8_accelerator.xsa](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/hardware/export/crc8_accelerator.xsa): the export the original Vitis platform was created from, including the bitstream |
| C application, linker script | Included |
| Bitstream | Included; the hardware configuration only. The application was downloaded separately over JTAG in the original setup. |
| Original Vivado reports | Timing (routed), system utilization (placed), peripheral utilization (synthesized) in [hardware/reports/](https://github.com/mattdisk/FPGA_crc8_accelerator/tree/main/hardware/reports) |
| Not included | Vivado `.xpr` project, generated IP output products, HDL top-level wrapper, Vitis workspace/BSP, `xparameters.h`, application ELF. All are machine-specific or regenerated by the tools. |

How far each workflow is supported (none of these have been tested from this repository):

- **Standalone RTL simulation:** supported directly. Add both files in `rtl/` to a Vivado project (or another VHDL simulator), set `crc8_core_tb` as the simulation top, and run behavioral simulation.
- **Vivado hardware reconstruction:** the inputs are present. A new Vivado 2024.2 project for the Basys 3 board would add `hardware/ip_repo/` as an IP repository, then add the block design (with its `ip/` folder) and the constraints. The tools would then regenerate output products and create the HDL wrapper. This requires the Digilent Basys 3 board files and some manual project setup, and may require IP updates or regeneration. An identical bitstream or identical timing is not guaranteed.
- **Vitis software platform:** create a standalone MicroBlaze platform from the provided XSA (which generates the BSP and `xparameters.h`), create an empty application, and add `main.c` and `lscript.ld`. This requires Vitis 2024.2.
- **Physical demonstration:** additionally needs a Basys 3 board, JTAG programming of the bitstream plus the application ELF, and a serial terminal at 115200 baud.

The [design document](https://github.com/mattdisk/FPGA_crc8_accelerator/blob/main/docs/design-and-validation.md#reconstruction-guide) lists the original project settings and the details of each workflow.
